## 一、现象描述

```bash
# 立即生效 ✅
rm /data/user/10/com.example.app/files/xxx

# 不受控，需要 drop caches ❌
rm /data/user/10/com.example.app/xxx
```

## 二、根本原因：目录层级与 dcache/inode cache 的关系

### 目录结构对应关系

```plain
/data/user/10/com.example.app/          <-- CE 加密目录 (bind mount)
    ├── files/                           <-- 普通目录，直接 ext4
    │   └── xxx                          <-- 普通文件
    ├── cache/                           <-- 普通目录
    ├── databases/                       <-- 普通目录
    └── xxx                              <-- 特殊位置文件
```

### 关键：/data/user/10 是 bind mount

```bash
# 查看挂载信息
adb shell cat /proc/mounts | grep "user/10"

# 输出类似：
# /data/user/10 -> /data/data  (bind mount)
# 或
# /dev/block/xxx /data/user/10 ext4 ...

# 查看完整挂载层级
adb shell mount | grep data
```

## 三、核心原理：Page Cache vs Dentry Cache

### 3.1 两个路径的 Cache 机制不同

```plain
/data/user/10/com.example.app/files/xxx
        │
        ▼
    普通文件路径
    ┌─────────────────────────────────┐
    │  VFS Layer                      │
    │  dentry cache (目录项缓存)       │
    │  inode cache  (inode缓存)       │
    │  page cache   (文件内容缓存)     │
    └─────────────────────────────────┘
        │  直接操作 ext4
        ▼
    磁盘 inode 立即更新
    ✅ 立即生效
```

```plain
/data/user/10/com.example.app/xxx
        │
        ▼
    受 sdcardfs/FUSE/overlayfs 影响
    ┌─────────────────────────────────┐
    │  FUSE/sdcardfs Layer            │
    │  kernel dentry cache            │
    │  ────────────────────           │
    │  用户态缓存 (MediaProvider)      │
    │  或 sdcardfs 内核模块缓存        │
    └─────────────────────────────────┘
        │  间接操作，缓存未失效
        ▼
    底层删除了，但上层 cache 未同步
    ❌ 需要 drop caches 才生效
```

## 四、深层原因分析

### 4.1 CE (Credential Encrypted) 存储与 bind mount

```c
// kernel/fs/namespace.c
// /data/user/10 实际上是通过 bind mount 映射的

// 删除 /data/user/10/com.example.app/xxx 时
// 实际操作的是底层真实路径
// 但 dentry 在两个挂载点都有缓存

struct dentry {
    unsigned int        d_flags;
    struct dentry       *d_parent;   // 父目录 dentry
    struct qstr         d_name;      // 文件名
    struct inode        *d_inode;    // 对应 inode
    // ...
};

// bind mount 导致同一个 inode
// 在两个路径下都有 dentry 缓存
// 删除一个路径的文件时
// 另一个路径的 dentry cache 未必同步失效
```

### 4.2 sdcardfs 的缓存问题

```c
// fs/sdcardfs/inode.c (AOSP kernel)

// sdcardfs 是一个堆叠文件系统
// 它在自己的层面维护了 dentry cache

static int sdcardfs_unlink(struct inode *dir, struct dentry *dentry) {
    int err;
    struct dentry *lower_dentry;
    struct inode *lower_dir_inode;

    // 获取底层 dentry
    lower_dentry = sdcardfs_lower_dentry(dentry);
    lower_dir_inode = sdcardfs_lower_inode(dir);

    // 在底层文件系统删除
    err = vfs_unlink(lower_dir_inode, lower_dentry, NULL);

    // ❌ 问题在这里:
    // sdcardfs 自己的 dentry 缓存没有及时失效
    // d_drop(dentry) 可能没有被调用
    // 或者 dcache 的引用计数还在

    if (!err) {
        fsstack_copy_attr_times(dir, lower_dir_inode);
        // sdcardfs 层的 dentry 未必立即更新
    }

    return err;
}
```

### 4.3 dentry cache 引用计数问题

```c
// fs/dcache.c

// 当应用进程还持有某个 dentry 的引用时
// rm 操作会：
// 1. 从父目录的 hash 链表移除该 dentry ✅
// 2. 调用 inode->i_op->unlink() 删除 inode ✅
// 3. 但 dentry 本身因为引用计数 > 0
//    仍然留在内存中 (negative dentry 或 orphan)

void dput(struct dentry *dentry) {
    if (unlikely(!dentry))
        return;

    // 引用计数减1
    // 如果还有其他引用，dentry 不会被释放
    if (lockref_put_or_lock(&dentry->d_lockref))
        return;

    // 只有引用计数归零才真正释放
    dentry_kill(dentry);
}

// 关键：
// /files/xxx 下的文件通常没有额外引用
// /com.example.app/xxx 可能被 sdcardfs 上层持有引用
```

## 五、具体场景分析

### 场景一：files/xxx 为什么立即生效

```plain
进程 A: rm /data/user/10/com.example.app/files/xxx
         │
         ▼
    VFS: vfs_unlink()
         │
         ├── dir->i_op->unlink(dir, dentry)  // ext4_unlink
         │       │
         │       └── ext4: nlink-- , 释放 inode (如果nlink=0)
         │
         ├── d_delete(dentry)
         │       │
         │       └── dentry 变为 negative dentry
         │           或从 dcache hash 中移除
         │
         └── inode_dec_link_count()
                 │
                 └── 立即更新 inode.i_nlink

// 结果：
// 其他进程再 open/stat 该文件
// VFS 查找 dentry -> 找不到 (negative) 或 inode nlink=0
// ✅ 立即看到文件不存在
```

### 场景二：com.example.app/xxx 为什么需要 drop caches

```plain
进程 A: rm /data/user/10/com.example.app/xxx
         │
         ▼
    路径解析经过 sdcardfs / bind mount 层
         │
         ▼
    底层 ext4: 文件确实删除了 ✅
         │
         ▼
    但 sdcardfs dentry cache 未失效:

    ┌──────────────────────────────────┐
    │  sdcardfs dcache                 │
    │  dentry("/data/user/10/          │
    │    com.example.app/xxx")  ──────►│──► 指向已删除的 inode
    │                                  │    但 dentry 仍在 cache 中
    └──────────────────────────────────┘
         │
         ▼
    其他进程查找该路径:
    VFS -> 命中 sdcardfs dcache -> 返回旧的 dentry
    ❌ 看起来文件还存在 或 状态异常

// drop caches 之后:
echo 3 > /proc/sys/vm/drop_caches
         │
         ▼
    dcache 全部清空
         │
         ▼
    重新查找路径 -> 底层 ext4 -> 文件不存在
    ✅ 正确反映删除状态
```

## 六、验证分析

### 6.1 验证 bind mount 关系

```bash
# 查看 /data/user/10 挂载情况
adb shell cat /proc/self/mountinfo | grep "user/10"

# 输出解析:
# 36 25 8:1 /data/user/10 /data/user/10 rw,bind
#  ^         ^              ^
#  mount_id  source         target (bind mount)

# 查看是否有 sdcardfs
adb shell cat /proc/filesystems | grep sdcard
adb shell mount | grep sdcard
```

### 6.2 验证 dentry cache 状态

```bash
# 查看 dcache 使用情况
adb shell cat /proc/sys/fs/dentry-state
# 输出: dentry数量 unused数量 age_limit want_pages ...

# 查看 slab 中的 dentry 占用
adb shell cat /proc/slabinfo | grep dentry

# strace 跟踪 rm 操作的系统调用
adb shell strace -e trace=file rm /data/user/10/com.example.app/xxx
```

### 6.3 对比 inode 操作

```bash
# 删除前记录 inode
adb shell stat /data/user/10/com.example.app/xxx

# 执行删除
adb shell rm /data/user/10/com.example.app/xxx

# 立即检查（可能还能看到）
adb shell ls -la /data/user/10/com.example.app/

# drop caches 后检查
adb shell sync
adb shell "echo 3 > /proc/sys/vm/drop_caches"
adb shell ls -la /data/user/10/com.example.app/
```

## 七、本质差异总结

```plain
┌─────────────────────────────────────────────────────────────┐
│              文件系统层级关系                                  │
│                                                             │
│  /data/user/10/com.example.app/xxx                         │
│         │                                                   │
│         ▼                                                   │
│  [sdcardfs / bind mount 层]  <-- dentry cache 在这里残留    │
│         │                                                   │
│         ▼                                                   │
│  [ext4 底层]  <-- 文件实际已删除                              │
│                                                             │
│  ─────────────────────────────────────────                  │
│                                                             │
│  /data/user/10/com.example.app/files/xxx                   │
│         │                                                   │
│         ▼                                                   │
│  [ext4 直接操作]  <-- 删除立即同步到 VFS dentry              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

| 对比项 | files/xxx | 直接 xxx |
| --- | --- | --- |
| 文件系统层 | 直接 ext4 | 经过 sdcardfs/bind |
| dentry cache | 立即失效 | 残留未失效 |
| inode 操作 | 直接更新 | 底层更新，上层不知道 |
| 其他进程可见性 | 立即可见 | 需要 drop caches |
| drop caches 后 | 无影响 | 正确反映删除 |

## 八、解决方案

### 方案一：删除后主动 sync + drop caches

```bash
adb shell sync
adb shell "echo 3 > /proc/sys/vm/drop_caches"
```

### 方案二：代码层主动使 dentry 失效

```java
// 删除文件后，通知 VFS 使 dentry 失效
// 通过 inotify 或 fanotify 触发缓存更新

File target = new File("/data/user/10/com.example.app/xxx");
target.delete();

// 强制 VFS 更新
Os.sync();  // fsync all
```

### 方案三：内核层修复（根本解决）

```c
// 在 sdcardfs unlink 实现中
// 确保上层 dentry 也被正确 drop

static int sdcardfs_unlink(struct inode *dir, struct dentry *dentry) {
    int err = vfs_unlink(lower_dir_inode, lower_dentry, NULL);

    if (!err) {
        // ✅ 主动使 dentry 失效
        d_invalidate(dentry);  // 添加这行
        d_drop(dentry);        // 从 hash 中移除
    }
    return err;
}
```

### 方案四：使用正确的删除 API

```java
// 通过 installd 删除，走正确的内核路径
mInstaller.clearAppData(
    ps.volumeUuid,
    packageName,
    userId,
    StorageManager.FLAG_STORAGE_CE | StorageManager.FLAG_STORAGE_DE,
    ceDataInode);

// installd 会处理正确的 dentry 失效逻辑
```

**核心结论：问题根源在于 sdcardfs/bind mount 的堆叠文件系统导致 dentry cache 与底层 ext4 实际状态不一致，drop caches 强制清空 dcache 后重新查找才能反映真实状态。**
